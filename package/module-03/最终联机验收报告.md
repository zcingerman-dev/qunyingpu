# 最终联机集成与回归验收报告

完成范围：临时互联网房间接入身份、国战、斗地主、点将单挑。复用已验收的 ACTION / EVENT / SNAPSHOT 与 Host 权威架构，保留原本地单机和第一阶段本地联机入口。未修改武将技能、平衡、原扩展加载器或个人资料。

## 1. 接入与架构

| 模式 | 总人数 | 真人 / AI | 选将 |
| --- | --- | --- | --- |
| 身份 | 2～10 | 至少2真人，其余可为AI | 逐席单将，随机身份，标准身份规则 |
| 国战 | 2～12 | 至少2真人，其余可为AI | 逐席主副将，沿用当前合法配对规则 |
| 斗地主 | 3 | 2真人＋1AI，或3真人 | 逐席单将 |
| 单挑 | 2 | 2真人 | 点将单挑，逐席单将 |

真人座位由信令成员身份绑定，不接受 Client 自报 seat。Host 自己也经过 ACTION 输入。AI 仅在 Host 的原生引擎内执行。第三个真人与第三座位重连已在真实 WebRTC DataChannel 中验证；12真人大厅、权限和座位容量由自动信令测试验证，没有宣称已做12台真实设备压力测试。

```text
真人操作 → ACTION（锁定至ACK） → Transport → Host验证 → 原生Game Engine
    → EVENT / SNAPSHOT → buildPlayerView(playerId, seat) → 各Client的只读Replica
AI操作 → Host原生AI → 同一个Game Engine → 同一玩家视图边界
```

WebSocket 只传房间、在线状态、Ready、开始、offer / answer / ICE和重连认证。游戏操作、快照和结算经有序 WebRTC DataChannel 传输。信令没有游戏核心、牌局数据库或完整 GameState。

每个 Client 仅收到自己的手牌、身份、暗将及当前私有选择，其他玩家只展示公开身份/明将、手牌数等白名单字段。国战主副将分别判断公开状态。Host RNG 在引擎导入前安装，选将随机、洗牌、摸牌均在 Host 执行。每位玩家的胜负按所属阵营独立生成，不沿用最后被接管角色的结果。

## 2. 本轮修改

- 增加四模式、总人数、真人／AI人数设置、逐席真人选将及合法AI选将；多人大厅列出真人与AI。
- 统一多人座位与断线暂停，所有真人连回后通过新的 PlayerView Snapshot 恢复；Client刷新保持 playerId、座位、当前选择，宽限2分钟。
- 接通原生卡牌、目标、响应、技能分支、背面牌选择及 chooseToMove 排序；目标标出座位，技能选项显示说明。
- UI在 Host ACK前锁定提交；Host对同ID ACTION去重，拒绝重复排队、旧提示版本、假引用、越权座位和直接写入状态。
- 保持 protocolVersion=1，信令与DataChannel均拒绝不匹配版本；DataChannel添加版本外壳，ACTION字段及原阶段游戏语义保持不变。
- 增加可填写 TURN、强制中继、连接/认证/发送/ACK超时提示；已成功连接时不会因无用的STUN候选失败误报断线。
- 选将应用失败不提前冻结或越过当前座位；清理大厅已离开成员的旧等待状态，避免新成员占同座位后被旧记录阻塞。

维护文件均相对本包根：`module-03/network-options.js`（模式/ICE配置/点击门）、`network-selection.js`（选将适配）、`network-host.js`（原生Host）、`network-view.js`（唯一状态披露边界）、`network-session.js`（房间/权威队列/重连）、`network-rtc.js`（DataChannel）、`internet-ui.js` / `internet.html` / `network.css`（操作面板）、`bridge.js`（可选联机选将分支）、`play_server.py`（静态资源白名单）、`signaling/server.mjs`（多人信令）。普通游戏核心不依赖WebRTC。

本机HTTP调用继续使用相对地址 `./api/state`、`./api/launch`、`./api/match/{id}`，不得写死盘符、用户名或部署端口。跨电脑唯一需要显式填写的外部服务为信令、STUN、TURN地址；房间码不包含服务地址。双方各自启动自己的包体，不开放个人资料HTTP服务。

## 4. 最小人工矩阵

先启动群英谱与 `启动信令服务.cmd`。同机可开多个独立标签页；跨电脑时各自运行本机包体，填写同一个可访问的信令地址。Host选模式和人数，创建房间；Client输入6位码加入，全部真人Ready后仅Host开始，再逐席选将。

| 局 | 配置 | 最少检查 |
| --- | --- | --- |
| 身份 | 4人，3真人＋1AI | 三席分别选将；第三真人可操作；只有自己的身份和手牌可见；AI能够推进回合 |
| 国战 | 4人，2真人＋2AI | 合法主副将；对方暗将隐藏；明置后公开；选择目标能分辨座位 |
| 斗地主 | 3人，2真人＋1AI | 地主/农民、真人出牌与响应、AI行动及团队结算 |
| 单挑 | 2真人 | 双方选将、出杀、响应闪、一次技能选择、死亡与胜负 |

各局先验证1个正常回合。至少把单挑或斗地主一局走到结算，双方结果应各自正确。其余模式的原生结算已有自动场景证据。

上述任一局再做：快速双击同一牌，确认只选中一次；Client在当前选择时F5或断网数秒后恢复，座位、手牌、牌局与选择不变；Host离开应关闭全部Client房间。返回单机开一局，确认原入口可用。

F12可用 `window.networkAudit.currentView()`：其他人只有数字手牌数，`own.hand`仅含自己的牌，未公开身份为unknown，暗将为“未明置武将”。展开“联机事件与状态核对”，两端在静止状态下的公开状态校验值应一致。Client不加载正式游戏引擎；自己的快照副本修改不会回写Host。此审计对象仅复制已收到的数据。

有TURN服务后，双方在“连接设置”填写 `turn:服务地址:3478?transport=udp`（或服务提供的 `turns:` 地址）、用户名、凭据，勾选“强制TURN中继”，新建一局；连接状态应显示“TURN中继已连接”。再取消强制中继验证自动候选回退。没有服务时无需填写占位凭据来尝试正常直连。

## 5. 已知限制

- 用户当前没有可用TURN服务。已验证ICE配置、强制relay分支及本机不可达TURN的连接超时提示；尚未验证公网中继实际转发、复杂NAT穿透或不同运营商网络。ICE的all策略提供直连/中继候选，relay策略只允许中继，遵循[WebRTC标准](https://www.w3.org/TR/webrtc/)。
- Host退出、刷新或断线会关房；没有Host Migration。Client等待恢复超过2分钟关闭房间，不恢复历史动画。
- 联网入口采用上表基础规则，立储/择途等身份变体、个人DIY与自定义代码仍在原本地入口使用，本轮未扩大其联机范围。
- 已覆盖常用原生选择接口。技能自行绘制且没有暴露合法操作节点的特殊界面会提示并暂停；不会自动选项或绕过权限。这些界面没有逐武将全量验收。
- 隐藏信息针对Client隔离；Host作为权威执行者仍拥有完整牌局状态，没有声称可以对恶意Host隐藏信息。
- 未实现排位、账号、好友、观战或云端游戏服务器。公网信令和TURN需使用者自行配置。
